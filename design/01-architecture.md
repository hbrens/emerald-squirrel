## 两层知识库分工

| 维度 | Part 1 笔记层 | Part 2 导入层 |
|---|---|---|
| 来源 | LLM 写（基于对话） | 用户上传原始文档 |
| 读写 | LLM 可读可写 | LLM 只读，无写工具 |
| 存储 | SQLite + markdown 字符串（Q1） | SQLite + 向量索引（Q8） |
| 检索 | 纯文本 / FTS5（Q2） | 向量检索（Q3） |
| 写入纪律 | 继承「写入即维护」（Q3） | 无（不可写） |
| 确认机制 | write/delete 需用户确认 | 上传是用户主动行为，无需二次确认 |
| 量级 | 中（百-千条） | 大（多文档多 chunk） |

**为什么这么分**：导入的原始文档量大、检索密集、永不修改，RAG 收益最大；笔记是 LLM 写入高频场景，要算 line diff、要 LLM 工具操作，纯文本更顺手。两层各取所长。

## 整体数据流（一次「记一下 X」对话）

1. 用户在聊天页输入「记一下 X」
2. 后端 `/api/chat` 收到，喂 LLM（带 SYSTEM_PROMPT，见 04）
3. LLM 调 `search_notes(X)` 查重 → 命中 or 无命中
4. 命中：LLM 调 `read_note(id)` 读旧文 → 输出新版全文
5. LLM 调 `write_note(id, new_content)` → 后端发 proposal（diff preview）给前端
6. 用户在前端点「确认」→ 后端执行写入 → 返回成功
7. LLM 收到 tool result，输出一句话总结
8. 前端流式展示 + 工具时间线 + diff 卡片状态

## 整体数据流（一次「问 X」对话）

1. 用户输入「X 是啥来着」
2. LLM 决定查哪层：
   - 笔记里自己记的 → `search_notes`
   - 导入的参考资料 → `search_imports`
   - 都查 → 两个工具都调
3. 收到结果 → LLM 综合回答（带出处）
4. 前端流式展示

| 组件 | 选型 | 决策编号 |
|---|---|---|
| 后端框架 | Hono + Node TS（参考 htwm-wiki） | — |

## 不在本架构内

- git 版本管理（已移除）
- 跨会话记忆（仅会话内恢复）
- WeKnora 风格细 UI（实施期再做）
