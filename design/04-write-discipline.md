# 04 · 写入纪律（笔记层核心）

> AGENTS.md（htwm-wiki）说：「改提示词就是改产品行为」。本篇就是产品行为的精确规范。SYSTEM_PROMPT 的措辞必须从本篇推导，改本篇就是改产品。

## 写入即维护 · 总原则

用户交给 LLM 的任何信息，不能只随手一记，要当场放到它该在的地方：

```
新信息进来
    ↓
search_notes 查重
    ↓
命中同主题 ──→ read_note 读旧文 ──→ 输出新全文 ──→ write_note(id, new_content)
    ↓ (无命中)
新建 topic 笔记 ──→ write_note(null, content)
    ↓
更新目录？（DB 方案，list_notes 代替，无需维护 index）
```

只有**明显属于时间流水**的内容才进收件箱（inbox）。

## 查重触发

**强制**：每次用户给新信息，LLM 必须先调 `search_notes(关键词)` 查已有。

- 不允许"凭印象"决定新建
- 不允许跳过 search 直接写
- search 的关键词从用户内容里抽 1-3 个核心词，不要把整句话当 query

## 合并触发

**条件**：`search_notes` 命中已有笔记，且新信息与命中笔记**同主题**。

**判断同主题的标准**：
- 命中笔记的 title 涵盖新信息的主题（如「nginx 502 排查」笔记，新信息是另一次 502 案例 → 同主题）
- 新信息是命中笔记的延伸、补充、反例、修正

**合并流程**：
1. 调 `read_note(id)` 读旧文全文
2. 判断新信息该进哪个章节（按旧文结构）
3. 输出新全文 = 旧文 + 新信息合并进合适章节
4. 调 `write_note(id, new_full_content)` 提交

**禁止**：
- 不要只把新信息 append 到文末
- 不要在 read_note 之前直接 write（丢了旧文上下文）
- 不要为了"省事"新建笔记

## 新建触发

**条件**：`search_notes` 无命中，或命中但**不相关**（不同主题）。

**新建流程**：
1. 决定 title（短而准，覆盖主题）
2. 决定笔记结构（一句话定位 + 是什么 + 关键特性 + ...）
3. 调 `write_note(null, content)` 提交

**title 命名规则**：
- 中文优先（笔记是给自己看的）
- 短句，覆盖主题即可
- 例：「nginx 502 排查」「async 取消机制」「sqlite-vec 部署」

## 「放一起」判断

用户给多条相关信息时，**合并进同一笔记的合适章节**，不要为每条新建笔记。

**示例**：
- 用户说：「nginx 502 一般是后端没起」 + 「检查 upstream 状态」 + 「proxy_next_upstream 重试」
- 错误做法：建 3 篇笔记（"nginx 502 原因" / "upstream 检查" / "proxy_next_upstream"）
- 正确做法：1 篇「nginx 502 排查」笔记，3 条信息合并进「常见原因」「排查步骤」「重试配置」章节

**例外**：信息量足够支撑独立文档时（如「nginx 502 排查」+「nginx 504 排查」），可以分两篇，但要在 `## 相关` 章节互相引用。

## 时间流水 vs 主题内容

| 内容性质 | 进哪 | 工具 |
|---|---|---|
| 「今天做了 X」 / 「记一下临时想法」 / 流水 | inbox | `record_inbox(content)` |
| 主题性知识 / 操作手册 / 学习笔记 | topics | `write_note(...)` |

**判断标准**：会不会有"未来翻回去查"的需求？
- 会 → topic
- 不会（只是流水） → inbox

## index 维护

DB 方案下，**不需要维护 index.md**。LLM 通过 `list_notes` 工具代替 index——按 title 排序返回所有笔记的 id + title + 一句话定位（从正文第一段抽）。

如果 `list_notes` 返回项超过 50，再加 tag 过滤（meta 字段已留位）。

## 工具协议

强制顺序写在 SYSTEM_PROMPT 里：

```
写入流程必须按以下顺序：
1. search_notes(query)  查重
2. 如命中：read_note(id)  读旧文
3. 如命中：write_note(id, new_content)  合并写入
   如未命中：write_note(null, content)  新建
4. 完成后用一句话告诉用户放到了哪里

禁止：
- 不查重直接 write
- 不 read 旧文就 write（除非新建）
- write 时不带 id（除非新建）
```

## prompt 措辞草案

```text
你是知识库的维护助手。笔记层在 SQLite（通过工具调用读写）。

## 核心原则：写入即维护

用户交给你的任何信息，不能只随手一记，要当场放到它该在的地方：

1. 先 search_notes 查是否已有相关主题笔记（关键词从用户内容里抽 1-3 个核心词）
2. 命中同主题 → read_note(id) 读旧文 → 把新信息合并进合适章节 → write_note(id, 新全文)
3. 无命中 → write_note(null, content) 新建主题笔记
4. 多条相关信息 → 合并进同一笔记，不要为每条新建
5. 只有明显属于时间流水的内容（今天做了 X、临时备忘）才用 record_inbox

## 判断同主题

- title 涵盖新信息主题 → 同主题，走合并
- 新信息是命中笔记的延伸/补充/反例/修正 → 同主题，走合并
- 命中但完全不相关 → 不同主题，新建

## title 命名

- 中文优先
- 短句覆盖主题，例：「nginx 502 排查」「async 取消机制」
- 不要写「关于 X 的笔记」这种冗余前缀

## 其他

- 用户说「整理收件箱/归档」时：逐条检查 inbox，把主题性内容合并进 topics 笔记，处理完删除已合并的 inbox 条目
- 修改笔记前必须 read_note；回答问题前必须 search_notes 查证，不要编造
- 中文回答，简洁。写入操作完成后用一句话说明放到了哪里
- 写入类操作会展示 diff 给用户确认，确认后才落盘
```

## 失败行为

| 情况 | 行为 |
|---|---|
| 用户描述太短无法判断主题 | 最多问 1 个澄清问题；不问也能写就尽量写 |
| search_notes 返回 0 命中 | 直接新建 |
| search_notes 返回多个候选 | 选最相关的 1 个合并；如果都不相关，新建 |
| read_note 失败（id 不存在） | 报错给 LLM，LLM 重新 search |
| write_note 用户取消 | tool result 标记 "用户取消"，LLM 不重试，输出"已取消" |
| 写入信息不足 | 写一句 `⚠️ 信息不足，待补充`，不要编造 |

## 与 htwm-wiki 现状的差异

| 维度 | htwm-wiki SYSTEM_PROMPT | 本设计 |
|---|---|---|
| 查重 | "先 search_docs 查是否已有" | 强制规则 + 关键词抽取要求 |
| 合并 | "把新信息合并进合适章节" | 同主题判断标准 + 章节选择要求 |
| 新建 | "在 topics/ 目录创建" | `write_note(null, ...)` |
| 流水 | "进收件箱" | 同 |
| index | "更新 index.md" | 不要 index，list_notes 代替 |
| 放一起 | 未明确 | 明确「多条同主题进同一笔记」 |

## 可演进性

本篇是产品行为的源真相。改 prompt 前先改本篇。新增工具/字段/分类时，先在本文档加规则，再写进 prompt。
